# Спецификация изменений harness OpenCode

Предлагаю сохранить один глобальный law-файл, разрешить три узкие операции — безопасный просмотр PM2, чтение метаданных сессий и push в авторизованную тематическую ветку — и заменить безусловный `HALT` диагностикой конкретного этапа. Сокращать число `deny` само по себе не цель. Критерий приёмки — разрешённая операция проходит у нужной роли, а соседняя опасная операция по-прежнему отклоняется.

Спека приведена в ответе. Отдельный выходной путь в задании не указан. Прочитаны только два названных отчёта. Файлы и конфигурация не менялись, секреты не читались.

## Что установлено

- В конфигурации 208 объектов `permissions` с эффектом `deny` или `ask`, включая 55 глобальных запретов навыков. Для `pm2 jlist` и `pm2 describe` найдены прямые совпадения на строках 526 и 528. Форма `git push -q -u origin HEAD` не покрыта разрешением `git push -u origin *`. Для составной команды `git checkout … && git push …` причина конкретного отказа не установлена. Порядок объединения глобальных и ролевых правил также не измерялся. [Аудит конфигурации](/root/workspaces/tools/docs/codex-audit/20261128/06-analyst-atom-audit-config.md)
- **Проверено 0 из 15 сессий.** Среда отклонила запуск `sqlite3` до старта процесса с диагностикой `approval required by policy, but AskForApproval is set to Never`. Глобальный `ask` для `sqlite3 *` и запрет запуска на уровне хоста — разные точки принятия решения. `EROFS` при записи лога указан во входных фактах задания. Частота блокировок в рабочих сессиях неизвестна. [Аудит сессий](/root/workspaces/tools/docs/codex-audit/20261128/06-analyst-atom-audit-sessions.md)

## Решения

### 1. Разрешения определяются операцией и контуром

Целевой порядок для затронутых операций — базовое право роли → узкое разрешение на проверенную операцию → окончательный запрет разрушительного действия или раскрытия секрета. Для действий вне роли разрешение отсутствует. `ask` имеет смысл только в интерактивном контуре с доступным подтверждением. Первым шагом на установленном harness нужно измерить итоговое решение при конфликте глобального и агентного правил, в частности для `audit` с собственным `shell * allow`. Само перемещение строк JSONC не доказывает приоритет. [Аудит конфигурации](/root/workspaces/tools/docs/codex-audit/20261128/06-analyst-atom-audit-config.md)

| Операция | Разрешить | Граница |
|---|---|---|
| PM2 | `pm2 ls` в авторизованном контуре после проверки состава вывода. Для `describe <id\|name>` и списка в формате JSON дать одну доверенную обёртку с двумя режимами. Она возвращает только ID, имя, статус, uptime и счётчик рестартов. | Обёртка сама формирует ответ из разрешённых полей. Сырой JSON, `env`, аргументы запуска и исходный вывод ошибок не попадают в контекст, лог или временный файл. Прямые `jlist`, `prettylist`, `env` и непроверенные `describe`/`show` остаются закрыты. |
| Git push | Для роли доставки разрешить один `origin`, одну исходную ветку и один авторизованный одноимённый topic-ref. Допустить `HEAD` или имя текущей topic-ветки, `-q`/`--quiet` и `-u`/`--set-upstream` в поддерживаемом порядке, включая `git push -q -u origin HEAD`. | До исполнения проверить фактический push URL, текущую ветку и единственный итоговый ref назначения. Отклонять force, включая `--force-with-lease`, `-f` и `+refspec`, а также delete, mirror, all, `--no-verify`, защищённое назначение и неизвестные опции. Применять проверку к разобранным аргументам. Если matcher умеет только glob, передать операцию узкой команде доставки. Расширение до `git push * origin *` небезопасно. |
| SQLite | Разрешить роли аудита именованную операцию чтения известной БД сессий через `mode=ro`. Для хоста с `AskForApproval=Never` предусмотреть явно разрешённую точку входа без CLI. | Разрешение ограничено заданной БД, набором запросов и полями результата. Оно не открывает произвольные SQL, пути, `sqlite3 *` или универсальный интерпретатор. |

Для Git приёмка охватывает также влияние настроек remote на итоговое назначение, сокращённые и объединённые флаги и разбор команд с `&&`. Если harness не может определить границы команды, разрешение выдаётся только отдельному вызову проверенной операции. Испытания push проводятся на изолированном локальном remote.

### 2. Один глобальный law-файл, проектные правила ниже

Использовать уже подключённый `~/.config/opencode/AUTO-GITHUB-LAW.md` как единственную глобальную запись `instructions`. Это сохраняет действующие правила доставки и не требует миграции пути. Проектный `AGENTS.md` дополняет глобальные ограничения в пределах выбранного проекта. Эффективную загрузку обоих уровней проверить у каждой настроенной роли, включая делегированную, и после compaction. В law-файле закрепить пять правил на английском языке.

1. Перед выводом «заблокировано» назвать операцию, цель, роль и последнюю диагностику. Перепроверить доступ дешёвой разрешённой проверкой именно этой возможности. Явный отказ политики завершает попытки выполнить отклонённую операцию.
2. Перед выводом «нет информации» выполнить релевантный поиск. Для локального кода использовать проектный MCP, для интерфейса библиотеки — Context7, для публичной документации — websearch. Записать источник, область поиска и результат. Недоступность источника и пустая выдача — разные результаты. Внешнему поиску передавать только публичные термины.
3. Вести в том же файле краткий реестр возможностей с назначением, контуром и способом проверки. Фактическую доступность получать из списка инструментов текущей сессии и разрешённого пробного чтения. Флаг `disabled:false` сам по себе не подтверждает работоспособность.
4. Для `tmux-send` выбирать окно по точному заголовку в указанной сессии, требовать единственное совпадение и адресовать найденную панель по стабильному ID. При нескольких панелях без заданного адресата, совпадениях заголовков или смене цели отправку остановить.
5. Секреты хранятся только в `/root/workspaces/secrets/`. Содержимое не передавать в модель, поиск, stdout, логи или индексы. Доверенный клиент может приватно использовать назначенный ему credential для разрешённой операции.

**Навыки.** Для `audit` и `verifier` открыть `audit` и `verify` по назначению. `incident-response` и `postmortem-writing` открыть в контуре разбора инцидентов, используя существующие роли. Проверять конкретные установленные имена до изменения wildcard. Загрузка навыка не расширяет права на shell, запись, управление сервисом или публикацию. Массовая отмена всех 55 запретов не требуется.

**MCP.** Первым кандидатом на включение выбрать `repowise` для чтения одного разрешённого проекта. Он сконфигурирован с `--no-workspace`, поэтому до включения нужно показать, как запрос однозначно выбирает проект, и получить известный ответ из его кода. `codebase-memory-mcp` пока оставить выключенным. В аудите нет свидетельства готового разрешённого индекса или дополнительного сценария, которому недостаточно первого сервера, а операции индексирования и удаления отдельно закрыты. Основание пересмотреть решение — конкретный запрос к существующему изолированному индексу. [Аудит конфигурации](/root/workspaces/tools/docs/codex-audit/20261128/06-analyst-atom-audit-config.md)

### 3. Чтение сессий, журналы и усечённый вывод

Для read-only Codex предусмотреть доверенный reader на базе библиотеки SQLite. Хост должен явно разрешать эту операцию. Reader открывает фиксированный URI с `mode=ro`, включает `query_only` и выполняет предопределённые запросы к проверенной схеме. Начальный контракт — идентификатор сессии и доступные счётчики. Сырой `part.data` в ответ не входит. На стенде с активным WAL проверить видимость последней подтверждённой записи и работу с правами реальной роли. Если чтение требует дополнительной записи для обслуживания WAL, возвращать точную диагностику. Права записи в каталог рабочей БД роли аудита не выдавать.

Для read-only запуска предпочесть уже доступный поток журналирования хоста, если установленная версия поддерживает такой режим. Если файловый лог обязателен, предусмотреть отдельный приватный writable-каталог на запуск, доступный только для логов. Приёмка включает **старт, чтение сессии и завершение** без `EROFS`, с сохранением read-only режима проекта и БД.

При `tool_output.max_lines=40` и `max_bytes=81920` агент, получивший признак усечения, должен прочитать полный сохранённый вывод по доверенной ссылке частями до EOF, прежде чем делать вывод обо всём результате. Это правило применяется только к данным, доступным роли. Если harness не предоставляет полный файл, агент фиксирует неполноту и повторяет разрешённое чтение с пагинацией, когда это возможно. Параметры compaction `auto:true`, `keep:10000`, `buffer:35%` сохраняются — аудит не установил, что они вызвали отказ. [Аудит конфигурации](/root/workspaces/tools/docs/codex-audit/20261128/06-analyst-atom-audit-config.md)

### 4. `codex-first` прекращает повторы, сохраняя статус этапа

По статическому аудиту после трёх коррекций `codex-first` отправляет в сессию текст `HALT` через `session.prompt`. Доказательств остановки процесса или конкретной рабочей сессии нет. Риск ложной остановки существует даже в проектной задаче без правок — детектор учитывает делегирование как самостоятельное условие. [Аудит конфигурации](/root/workspaces/tools/docs/codex-audit/20261128/06-analyst-atom-audit-config.md)

Предлагаемая семантика — требовать `RUNNER` только для этапа, где такая проверка применима. После исчерпания лимита прекращать повторные prompts и один раз сообщать, какой критерий остаётся непроверенным. Обязательная проверка продолжает блокировать объявление этапа завершённым. Независимая разрешённая работа может продолжаться. `no-tails` и `todo-gate` оставить без изменений, а их взаимодействие проверить совместной последовательностью событий `session.idle`.

## Атомы реализации

Имена новых файлов ниже проектные. `opencode.jsonc` обозначает существующий глобальный конфиг. Каждый атом затрагивает не более трёх файлов. Проверки и откаты описаны для будущей реализации.

| № | Действие и файлы | Приёмочная проверка | Откат и радиус |
|---|---|---|---|
| 1 | **Зафиксировать порядок разрешений.** Один новый файл тестов `permission-matrix.test.*` | На установленной версии получить фактические решения для конфликта global/role, точного совпадения, неизвестной формы и цепочки `&&`. Включить `build`, `audit` и `verifier`. | Убрать тест. Только стенд. |
| 2 | **Открыть безопасную интроспекцию PM2.** `opencode.jsonc`, `pm2-inspect`, `permission-matrix.test.*` | `ls`, список JSON и описание процесса работают. Синтетический маркер в env и аргументах отсутствует в stdout, stderr и логе как при успехе, так и при ошибке. Прямой сырой запрос закрыт. | Вернуть прежние правила и отключить обёртку. Только чтение PM2 выбранного контура. |
| 3 | **Нормализовать push.** `opencode.jsonc`, при необходимости `topic-push`, `permission-matrix.test.*` | На локальном remote обе перестановки `-q`/`-u` обновляют ровно одну разрешённую ветку. Для каждого запрещённого флага, чужого URL и защищённой ветки решение отрицательное, refs неизменны. | Вернуть прежнюю политику push. Радиус — роли доставки и их авторизованные remote. |
| 4 | **Открыть навыки по контурам.** `opencode.jsonc`, `permission-matrix.test.*` | Нужные роли видят и загружают конкретные навыки. Контрольный вызов записи у read-only роли остаётся закрыт. | Вернуть прежние skill-правила. Радиус — каталог навыков затронутых ролей. |

| 8 | **Изолировать запись лога.** Существующий профиль запуска read-only роли, `readonly-launch.test.*` | Полный цикл с reader проходит без `EROFS`. Запись в каталог проекта и БД запрещена. **Порядок внедрения.** Сначала измерить matcher атомом 1. После этого менять разрешения PM2, Git и навыков по отдельности. Атомы 7 и 8 принимать совместным прогоном под реальной read-only ролью — успешное чтение библиотеки на стенде само по себе не подтверждает устранение `EROFS` или доступ хоста. Наибольший радиус у глобального law-файла и `codex-first`, поэтому их сначала проверяют в отдельном профиле harness. Все эксплуатационные проверки в таблице остаются критериями будущей приёмки.

# Спецификация: почему агент не смог решить задачу с сертификатом и что менять в инструкциях

- Дата: 2026-11-28
- Источник: полный разбор сессии `build` (kint-b24), журналы `letsencrypt.log`, `admin_access.log`, `letsencrypt-requests_access.log`, база NPM `database.sqlite`, git-история `tools` и `kint-b24`
- Связи: `system/services/proxy-manager/AGENTS.md`, `/root/.config/opencode/AUTO-GITHUB-LAW.md`, `tools/bin/codex-role`, `tools/bin/npm-api`, `tools/bin/npm-cert-restore`
- Адресат: агент-конфигуратор, который правит инструкции и запускатель агентов

---

## 1. Пользовательская задача

Владелец: «сайт `kint.b244.ru` должен открываться во всех браузерах без предупреждения, полноценный рабочий сайт». Изначально: браузер показывал `ERR_SSL_UNRECOGNIZED_NAME_ALERT` / «Подключение не защищено».

Фактический итог сессии: **решение найдено**, но через 4 часа, ~15 неудачных попыток, истерику владельца и сожжённые лимиты. Сертификат восстановлен из базы NPM и отдаётся как настоящий Let's Encrypt (`issuer=CN=YE2`, `notAfter=Feb 23 12:59:44 2027 GMT`, `curl → 401, ssl_verify_result=0`).

## 2. Хронология провала (стадии)

| Стадия | Что я сделал | Что было правильно | Что было ошибкой |
|---|---|---|---|
| 1 | Увидел пустые файлы `custom_ssl/npm-49/{fullchain,privkey}.pem` (0 байт, 19:43) | Зафиксировал факт | Не сделал резервную копию и не проверил, где ещё хранится материал сертификата |
| 2 | Сгенерировал самоподписанный `openssl req` | Сайт поднялся | Нарушил будущий запрет владельца, подменил данные вместо восстановления |

| 6 | 8 попыток выпуска через API NPM | Перешёл на штатный путь | Каждый `PUT` хоста обнулял файлы сертификата, дважды уронил https |

## 3. Почему я ходил по кругу (5 почему)

1. **Почему повторял одно и то же?** Каждый раз лечил симптом: файл пуст → сгенерировал файл; редирект мешает → снял редирект.
2. **Почему лечил симптомы?** У меня не было модели состояния системы: какие компоненты хранят истину (БД NPM, `custom_ssl`, `letsencrypt/live`, `meta` сертификата).
3. **Почему не было модели?** Я начал действовать сразу, без инвентаризации источников состояния; правило «сначала карта, потом правки» нигде не записано.
4. **Почему нет правила?** Инструкции требуют «доказательств» и «микро-атомов», но не требуют построить карту компонентов и данных перед восстановлением сервиса.
5. **Почему карта не появилась и позже?** Не было механического гейта: после двух неудачных гипотез никто не заставляет остановиться и выписать таблицу «гипотеза → ожидание → наблюдение».

**Корень:** отсутствие обязательного артефакта «карта состояния сервиса» и отсутствие жёсткого лимита гипотез. Отсюда цикл: попытка → отказ → новая попытка того же класса.

---

## 4. Что именно мешало (по фактам)

1. **Ложная посылка «сертификат утерян».** Не проверил `certificate.meta` в `database.sqlite` — там лежал полный PEM (4804 байта + ключ 241 байт), запись 49. Проверка заняла бы одну команду.
2. **Доверие к тексту ошибок вместо чтения кода.** Ошибка LE «likely firewall problem» увела меня в сетевую диагностику на полтора часа.
3. **Нет запрета на самоподписанные сертификаты на старте.** Запрет появился в законе контура только к концу сессии.
4. **Гонка писателей.** Другая сессия одновременно правила NPM (`admin_access.log`: `172.28.0.1 POST /api/tokens`), из-за чего файлы обнулялись повторно, а я считал это «своим» сбоем.
5. **Мои же инструменты давали ложные сигналы:** `codex-role` считал `rc=0` при текстовом отказе, потом давал ложный `nochange=1`, потом ложный `refusal=1`. Каждый дефект инструмента стоил отдельного прогона.
6. **Дисциплина атомов.** Запускал атом PDF в том же рабочем дереве, что и атом бюджета тестов — пришлось убивать процесс и перезапускать.
7. **Делегирование владельцу.** Присылал «Контрольная точка: сделайте в панели…» — прямо запрещено; это главный источник истерики.

---

## 5. Почему владелец дошёл до истерики

1. Я отвечал **оправданиями и диагнозами**, а не результатом; каждое сообщение заканчивалось «нельзя, потому что…».
2. Я **просил его действовать** (панель, команды) при прямом запрете делегировать.
3. Я **дважды уронил https** своими же правками (обнуление файлов при `PUT`).
4. Я **менял версии причин**: сначала «провайдер», потом «не знаю» — при этом сайт был недоступен.
5. Я **не показывал быстрый прогресс**: 4 часа без зелёного результата при наличии решения в БД.
6. Каждое моё сообщение было длинным и техническим, хотя просили одно: работающий сайт.

---

## 6. Почему сожжены миллионы токенов

1. 15 прогонов Codex по 900–1800 с, каждый с полным контекстом проекта.
2. Повторные прогоны одного и того же атома с одной и той же корневой причиной (бюджет тестов — 3 раза, выпуск сертификата — 8 раз).
3. Чтение больших логов целиком (`letsencrypt.log`, `admin_access.log`, `docker logs`) вместо `tail`/`grep`.
4. Полный прогон `bin/check.sh` и тестов после каждой мелочи вместо целевой проверки.
5. Диагностические «круги»: 8 запросов к check-host по 15–50 узлов, каждый с ожиданием и разбором.
6. Работа без карты состояния → каждая новая попытка начиналась с нуля.

---

## 7. Критика себя: как я пришёл к правильному решению

**Почему в итоге получилось:** я перестал лечить файлы и прочитал модель данных NPM — `/app/internal/certificate.js`: `writeCustomCert` пишет файлы из `meta.certificate`, `POST /upload` проверяет соответствие ключа, `disableInUseHosts` отключает хост на время выпуска. Из этого выросла правильная последовательность: достать PEM из `meta` → создать запись → `upload` → привязать к хосту.

**Что должно было привести туда сразу:**
- первый вопрос при «файл пуст» — не «как восстановить файл», а «где система хранит этот материал»;
- чтение исходников сервиса раньше, чем внешняя диагностика;
- проверка БД до любых правок файлов.

**Цена:** 4 часа и репутация. Метод, который сработал, был доступен на 10-й минуте.

## 8. Требуемые изменения в инструкциях (для агента-конфигуратора)

### 8.1 Инвариант «истина в сервисе» (обязательный раздел)

> Перед любым восстановлением сервиса агент обязан выписать карту состояния: какие хранилища содержат истину (БД, файлы, метаданные, кэш, резервные копии), какое из них авторитетно, и только после этого действовать. Правки файлов, которые сервис генерирует сам, запрещены — только через его API.

Проверка: в отчёте агента есть раздел «Карта состояния» с путями/таблицами.

### 8.2 Обязательная инвентаризация перед изменением

> Перед изменением: (1) найти документированный способ восстановления, (2) проверить БД сервиса на сохранённый материал, (3) сделать копию текущих файлов в датированный каталог, (4) только затем действовать.

Проверка: `ls` датированной копии и цитата из БД в отчёте.

### 8.3 Жёсткий лимит гипотез

> Две неудачные попытки одного класса → остановка, таблица «гипотеза / ожидание / наблюдение», новая гипотеза только из непроверенной строки таблицы. Третья попытка «того же, но иначе» запрещена.

Проверка: таблица в отчёте, третьей однотипной команды нет.

### 8.4 Запрет самоподписанных и ручных правок (уже есть, усилить формулировкой)

> Агент не создаёт сертификаты и не правит `custom_ssl/**` и `proxy_host/*.conf`. Восстановление — только через API NPM. Если материал утерян, ищется в `certificate.meta` БД NPM, затем в резервных копиях; при отсутствии — сообщается факт, замена не создаётся.

Проверка: `grep -c 'BEGIN CERTIFICATE' data/custom_ssl/*/fullchain.pem` соответствует записям БД, `openssl x509 -issuer` = выданный CA.

### 8.5 Механический гейт проверки TLS

> После любого изменения хоста: `openssl s_client -servername <host>` (issuer), `curl -s -o /dev/null -w '%{http_code} %{ssl_verify_result}'` (должно быть `0`), внешняя проверка с 3 узлов. Без этих трёх строк изменение не считается выполненным.

Проверка: три строки вывода в отчёте.

### 8.6 Запрет на делегирование (уже есть, усилить)

> Агент не присылает владельцу команд, шагов в интерфейсе и «контрольных точек». Всё, что можно выполнить с машины, выполняется. Владельцу сообщается только результат.

Проверка: в сообщениях нет императивов, адресованных владельцу.

### 8.7 Экономия токенов

> Логи читать только `tail`/`grep` с ограничением; не запускать полный набор тестов после каждой мелочи; один атом — одна целевая проверка; повторный прогон того же атома запрещён без новой строки в таблице гипотез.

Проверка: отчёт содержит команды с `tail`/`grep`, число прогонов на атом ≤ 2.

### 8.8 Изоляция атомов

> В одном рабочем дереве одновременно работает один пишущий атом. Запускатель обязан отказать второму запуску по тому же каталогу (lock-файл проекта).

Проверка: второй запуск завершается с `lock busy` и не пишет файлов.

### 8.9 Согласование параллельных сессий

> Перед правкой общего сервиса (NPM, docker, pm2) агент проверяет `admin_access.log`/`pm2 list` на активность других сессий и фиксирует найденное. Обнаружен чужой писатель → стоп и bd-атом с label `incident`.

Проверка: цитата из журнала в отчёте.

## 9. Готовый порядок восстановления (runbook, проверен в этой сессии)

```
1. sqlite3 -readonly database.sqlite "select id,provider,expires_on,length(meta) from certificate where domain_names like '%<host>%'"
2. если meta содержит certificate+certificate_key:
   POST /api/nginx/certificates           (provider=other, domain_names, nice_name)
   POST /api/nginx/certificates/<id>/upload  -F certificate=@cert.pem -F certificate_key=@key.pem
   PUT  /api/nginx/proxy-hosts/<host_id>  (certificate_id=<id>, ssl_forced=true, http2_support=true)
3. docker exec proxy-manager-app-1 nginx -t && nginx -s reload
4. openssl s_client -servername <host> -connect 127.0.0.1:443 | openssl x509 -noout -issuer -enddate
5. curl -s -o /dev/null -w '%{http_code} %{ssl_verify_result}' https://<host>/   -> ожидается 401 0
6. временные файлы с ключом удалить: safe-delete tmp <dir>
```

Инструменты: `tools/bin/npm-api`, `tools/bin/npm-cert-restore`.

## 10. Критерии приёмки самой этой спецификации

1. В инструкциях агента появились разделы 8.1–8.9 дословно или эквивалентно, с проверками.
2. `grep -c 'Карта состояния'` в файле инструкций → ≥ 1.
3. `grep -c 'Две неудачные попытки'` → ≥ 1.
4. `grep -c 'не присылает владельцу команд'` → ≥ 1.
5. Запускатель `codex-role` отказывает второму пишущему атому в том же каталоге (`lock busy`).
6. Повторный инцидент с сертификатом восстанавливается по runbook за ≤ 10 минут без генерации самоподписанных файлов.

## 11. Итоговая самооценка

Решение было в базе NPM с первой минуты. Я искал его в сети, в файлах, в провайдере и в чужих настройках, потому что не построил карту состояния сервиса и не прочитал его код. Всё остальное — следствие: круги, самоподписанные подмены, падения https, сожжённые лимиты, истерика владельца.

Что дало результат: отказ от «лечения файлов», чтение модели данных NPM и работа только через официальный API сервиса.
